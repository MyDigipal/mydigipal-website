On 22 October, Anthropic handed Agent Skills to the Agentic AI Foundation, the Linux Foundation body that already looks after the Model Context Protocol. The format that teaches an AI agent how to do a specific job is now owned by a neutral foundation rather than by the company that invented it.

Anthropic says more than 70 agent platforms have integrated the standard, including ChatGPT, Cursor, GitHub Copilot and VS Code. It also counts 1 million skills published and nearly 280 million installs.

For a marketing team, this removes the objection we heard most often when we suggested writing procedures as skills. Nobody wanted to spend weeks documenting their reporting rules for a tool they might drop next year. That risk has shrunk a lot.

## What changed on 22 October

A skill is still a folder with a SKILL.md file that explains a task, plus any scripts or reference documents the agent needs. The change is about who owns the format. Anthropic transferred the Agent Skills name and logo, the GitHub organisation and the agentskills.io domain. Engineers from Anthropic, Google, OpenAI and other companies will maintain the standard as individuals, with David Soria Parra and Mahesh Murag as lead maintainers.

The proposed roadmap starts with versioned releases, a formal proposal process and security guidance for people who write and install skills. Versioning matters, because until now each tool supported whatever it chose that month.

The move was widely expected. Simon Willison pointed out that he had predicted it last December, when Anthropic first called skills an open standard, writing at the time that he "wouldn't be surprised to see this end up in the AAIF". The timeline backs him up. Skills launched inside Claude in October 2025, became a published standard in December 2025, and have now followed MCP into the same foundation.

## Why portability was the missing piece

We have already covered how to build skills, from [the four pillars of a skill that scales](/en/blog/claude-skills-marketing-teams-build-once-scale-forever) to [packaging scripts and templates into one workflow](/en/blog/claude-agent-skills-custom-workflow-packages-marketing-teams). The method still applies, and the business case is now much stronger.

In most marketing teams we work with, people do not share one AI tool. The content writer lives in ChatGPT. The developer who maintains the website uses Copilot inside VS Code. The analyst uses Claude. Until this year, writing a procedure as a skill meant picking one of them and leaving the others with a PDF.

With a shared standard, the brand voice rules, the campaign naming convention and the monthly reporting checklist can sit in one folder that every tool reads. When the team changes tools or hires someone new, the folder stays.

There is also a quieter benefit. A procedure written for an agent has to be explicit. It forces the team to write down the rule that lived in one person's head, and that document has value even on the day nobody runs it.

## What "runs anywhere" does not cover

A common file format does not make every agent equal. Four things still vary from one tool to the next.

**Scripts.** A skill that runs a Python script to clean a CSV export needs an agent with a code execution environment. Some tools have one, some do not, and some restrict it by plan.

**Connectors.** If your reporting skill expects to pull data through an MCP connector to Google Ads or your CRM, that connector has to exist on the other side too. The skill travels and the plumbing stays where you built it.

**Triggering.** Each tool decides when to load a skill by reading its description. A vague description that works in one agent can be ignored in another. In our experience, this is the most frequent reason a skill seems to do nothing.

**Security.** Installing a skill means installing instructions, and sometimes code, written by someone else. The security guidance is on the roadmap, which tells you it does not exist yet. Until it does, read third-party skills before you install them, the same way you would vet a browser extension.

## How we write skills at MyDigipal

We use skills every day. Our campaign build rules, our conventions for client emails and the checks we run before sending a performance report all live as skills. A few habits have held up, and the open standard makes them more useful.

**Write the description as a trigger.** One sentence that says when to use the skill, with the words people actually type. "Use when creating or editing a Google Ads campaign" works better than "Advanced paid search knowledge".

**Keep tool-specific details out of the main file.** If a step names a feature that only exists in one product, move it into a reference file. The core procedure then stays readable by any agent.

**Give the reason behind each rule.** "Read every budget back after writing it, because a wrong currency unit can multiply spend by 100" gets followed. "Always double-check budgets" gets skipped. Agents, like people, respect rules they understand.

**Version skills like code.** Ours sit in a Git repository, with changes reviewed before they go live. When a skill misbehaves, we can see what changed and when.

## A portability test to run this month

One afternoon is enough to find out where you stand.

Pick the skill your team uses most. If you have none yet, write one for a task that repeats every week, such as turning a campaign export into a client summary. Then run it in two tools your team already pays for, on the same five real inputs.

Compare the outputs on a single criterion. Would you send this to a client after a light edit? Then note what broke. It is usually one of the four items above, and the fix is often small, such as a clearer description or a script moved into an optional step.

If both tools pass, the skill is portable and you can stop worrying about which assistant your next hire prefers. If one fails twice on the same step, rewrite that step rather than the whole skill.

## Our take

The argument for waiting has gone. Procedures written as skills can now follow your team from tool to tool, under a foundation that no single vendor controls. Start with three to five skills that cover the work you repeat every week, store them where your team can review them, and test them on every tool in use.
